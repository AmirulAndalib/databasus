This change lands after `restore-console-command-database-access`. Console commands started with `docker exec` cannot reach the metadata database of a container that generates its password at startup, which that change fixes; without it the `--list-admins` command in section 5 and the recovery path documented in sections 7 and 8 fail with an authentication error on a normal deployment.

## Completion notes

- **The rollback window closes once an administrator address has been changed.** Rolling the binary back on an instance whose owner still signs in as `admin` leaves an unused column behind and works. Rolling it back after the owner has moved to a real address does not: the old code looks the bootstrap account up by the text `admin`, finds nothing, `IsRootAdminHasPassword` fails, and the authentication screen alerts without clearing its loading state, so nobody reaches the sign-in form. The restored `Email != "admin"` privilege checks would freeze administrator management even if sign-in worked. It is a lockout rather than a takeover, and it is recovered by rolling forward again or by setting the address back to `admin` in the database. See design.md - Migration Plan.
- **The down step cannot restore the account the up step deleted.** The up step removes the seeded `admin` row when it was never claimed and is the only row in `users`. The down step drops the index and the column and does not try to bring that row back: on such an instance the old binary seeds the account again at startup, which is exactly where it was.
