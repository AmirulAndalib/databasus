## Completion notes

- **Rolling the binary back with the second factor on is an unannounced security downgrade.** The migration adds `users_settings.is_two_factor_auth_required` with a `false` default and creates `two_factor_codes`, so deploying the change alters nothing until an administrator turns the setting on. Rolling back with it off is uneventful. Rolling back with it on leaves a column the old code never reads, so password sign-in silently returns to one factor while the interface and the database still say the second factor is required. Nobody is locked out and nothing warns anybody, which is why it is written down: an operator rolling back has to know the instance stops asking for codes. See design.md - Migration Plan.
- **During a mail outage the sixth sign-in attempt within an hour reports the wrong cause.** A send that fails leaves its row behind, because the row is what the hourly cap counts, so after five failed sends the cap answers "too many codes requested" instead of "could not send the code". An operator diagnosing a dead mail server sees the misleading message from the sixth attempt on; `--disable-2fa` is the way out either way.
- **The pending sign-in records the account's password creation time.** The table carries `password_creation_time` beyond the columns task 1.1 enumerates, because the verification step refuses a pending sign-in whose account changed its password in between (design.md - Re-check the account at the verification step), and that check needs the value the password step saw. design.md - Keep the pending sign-in in a table now lists the column.
